# QuackAPI core review and remediation — 2026-09-07

## Remediation status

The findings below record the **pre-fix baseline** at `327001f`, including the
original evidence and recommendations. They are not a description of the final
branch. The `fix/review-hardening` implementation now includes:

| Baseline finding | Implemented remedy |
| --- | --- |
| Indirect policy bypass | Parser AST rewriting with resolved table identity; unsupported indirect sources fail closed when policies are active. |
| Public GraphQL catalog default | Empty registrations expose no tables; legacy open access requires an explicit global setting. |
| GraphQL policy bypass | Shared policy rewriting and verified claims binding for execution, with consistent catalog scope. |
| Auth vectorization and JWT edge cases | Per-row auth decisions, strict Bearer separator, literal claim names, and rejection of null time bounds. |
| Stale queue workers can affect later deliveries | Monotonic delivery generations required for ack/nack/renew, with an unexpired lease predicate. |
| Unbounded timeout retries and expiry starvation | Expired exhausted jobs dead-letter; recovery is no longer suppressed by unrelated live deliveries. |
| Missing execution/admission bounds | Query watchdog, response byte cap, bounded pending queue, GraphQL complexity bounds, and inherited outbound deadlines. |
| Rate-limit identity/isolation | Database-owned bounded buckets keyed by verified subject or digest; public token rotation falls back to IP. |
| Outbound worker startup exception | Scoped joining of already-started workers and capture of worker exceptions. |
| PostgreSQL JSON typing/SQL translation | Wire OIDs determine JSON types; lexical quoting protects literals/comments and explicit casts survive parameter translation. |
| SSE query executes twice on startup | Retain and stream the first result instead of executing a discarded probe. |
| Database destruction at thread exit | Request-scoped connections replace TLS retention of the last database. |

The last row was discovered during integration: the macOS crash stack ran from
`ThreadRequestCache::~ThreadRequestCache` into `DatabaseInstance` destruction and
`BlockAllocatorThreadLocalState::Initialize`. A deterministic C++ regression
checks that the database weak reference expires when its owner and request end;
it fails against the pre-fix binary. This addresses the lifetime defect directly
instead of treating a passing debugger run as proof that the crash disappeared.

New capability documentation is in [request limits](RESOURCE_LIMITS.md), the
middleware and native validation guides, and the FastAPI demand reports. The
benchmark harness preserves per-run evidence and excludes failed or semantically
invalid cells. Historical scoreboard numbers are not evidence of this branch's
performance.

Policy enforcement remains an application-route boundary, not a replacement for
database privileges. GraphQL remains the documented read-only subset. The native
validation work targets FastAPI/Pydantic use cases through DuckDB types; it does
not imply compatibility with arbitrary Python validators or every GraphQL
feature. Final build/test evidence is recorded in the pull request.

## Highest-priority findings

### P0: Row access and masking policies do not protect indirect reads

**Evidence:** `src/quackapi_policy.cpp:1093` detects protected table names by
searching handler SQL text, and returns unchanged SQL when no name matches
(lines 1103–1134). This does not resolve a view or macro to its underlying tables.
The ordinary REST handler invokes this rewrite at
`src/quackapi_server.cpp:2637`.

**Observed current-build reproduction:** create `private_rows` with one secret row; create
`public_view AS SELECT * FROM private_rows`; bind a deny-all row access policy
to `private_rows`. An unauthenticated route selecting the table returns 403.
An unauthenticated route selecting the view returns 200 and the secret row.

This means the table policy cannot currently be treated as database-wide row
security. Route SQL is developer supplied, so this finding does not imply that a
client can submit arbitrary SQL to every route. It does mean an otherwise
ordinary view-based endpoint can expose protected data.

**Recommended change:** enforce policies using resolved catalog/table identities
and bound query structure, including views, macros, nested queries, joins, and
schema-qualified references. Until enforcement is complete, reject unsupported
indirect reads of protected tables. A name-based view special case would leave
the underlying gap unresolved.

**Acceptance tests:** direct table and equivalent view/macro routes return the
same tenant-filtered and masked rows; unauthenticated requests fail closed;
quoted/schema-qualified references and joins preserve enforcement; public
unrelated tables remain readable. Include nested views and renamed objects.

### P0: Built-in GraphQL is public and defaults to the entire main catalog

**Evidence:** `src/quackapi_server.cpp:2118` explicitly declares built-in
`POST /graphql` public, before the ordinary auth/policy handler. The schema
endpoint is similarly public at line 2159. Named GraphQL routes check REQUIRE at
line 2052 but do not disable the built-in route.
`src/quackapi_graphql.cpp` interprets an empty global allowlist as open mode.

This behavior is an **existing documented contract**, not an accidental
regression: `test/sql/quackapi_graphql.test` asserts default open mode, reopening
access after dropping the last table, and independence of named mounts and the
built-in endpoint. Creating a protected named mount does not make the same data
private on `/graphql`.

**Observed current-build reproduction:** a named `/private-gql` route requires
an API key and returns 401 without it. The same unauthenticated query against
`/graphql` returns 200 and the protected table's secret row.

**Recommended change:** make catalog access opt-in, distinguish disabled,
explicit-open, and allowlisted modes, and keep an empty allowlist closed.
Require an explicit configuration to restore legacy open behavior. Include a
migration note and update the existing tests intentionally.

**Acceptance tests:** a fresh server exposes no tables through GraphQL;
registering one table exposes only it; dropping the final registration exposes
nothing; creating a named protected mount never creates a second public path to
its tables; schema discovery has the same authorization requirements.

### P0: GraphQL bypasses row access and masking policy enforcement

**Evidence:** named GraphQL dispatch at `src/quackapi_server.cpp:2074` supplies
only allowed tables and row limit to execution. `ExecuteGraphqlQuery` creates
its own connection and `SelectTableJson` at
`src/quackapi_graphql.cpp:234` generates a direct SELECT. The path never passes
verified claims to the REST policy rewriter. Built-in GraphQL has the same gap.

**Observed current-build reproduction:** with a deny-all row policy on
`private_rows`, an authenticated query through a named GraphQL route returns
200 and its secret row. This was tested in the same isolated database as the
view and public-endpoint reproductions.

**Recommended change:** route REST and GraphQL through one policy enforcement
layer. Allowlisting a table and authenticating a caller are not substitutes for
tenant row filtering or column masking.

**Acceptance tests:** the same authenticated identity sees identical protected
rows and masking through REST and GraphQL; unauthenticated GraphQL cannot query
a protected table, even if explicitly registered.

## Auth bugs fixed in this review

Changes are in `src/quackapi_auth.cpp`; regressions are in
`test/sql/quackapi_auth_edge_cases.test`.

| Fix | Previous behavior and evidence | Current implementation |
| --- | --- | --- |
| Per-row auth decisions | Mixed valid/invalid credentials passed to `quackapi_verify_auth` returned `true,true,true,true` when the first row was valid. All three auth bridge scalars read row zero. | Verification and authentication loop over every input row (lines 592, 615); authorization forwards the complete input vector (line 642). |
| Bearer scheme separator | `Authorization: Beareredge-valid-key` returned 200 with a valid API key. | Require whitespace after `Bearer` before parsing the credential (line 252); ordinary mixed-case `bEaReR key` remains accepted. |
| Literal JWT claim names | A signed top-level `tenant.id: "literal"` was returned as the nested `tenant.id` value `"nested"`; `role[0]` was dropped. | Enumerate `json_each` values directly (line 185), avoiding interpolation of claim names into JSONPath. |
| Explicitly null JWT time bounds | A correctly signed token with `exp:null` was accepted as though no expiry claim existed. The same logic affected `nbf:null`. | Reject present null NumericDate claims (line 343), preserving optional absence. |

The first-row issue is a security-relevant SQL scalar defect. Typical HTTP auth
calls evaluate one credential at a time; this review does not claim a direct
cross-request HTTP bypass from vectorization alone.

The new suite tests malformed/valid Bearer headers, alternating credentials,
both authentication paths, per-row authorization text, null time claims, and
literal dotted/bracketed claim names. It and the existing auth, JWT, policy, and
Quack bridge tests passed in the current-source run above.

Remaining auth work: specify issuer/audience requirements and key rotation,
preserve and validate claim types (including NumericDate handling), define
duplicate-claim rejection, and add malformed-token/size/fuzz tests. These are
follow-up work, not claims that this patch implements a complete JWT profile.

## Robustness and productionization

### P1: Queue deliveries lack ownership fencing

**Evidence:** `src/quackapi_queue.cpp:650` acknowledges by queue, job ID, and
`status='running'` only. Nack has the same issue at lines 689–745. Every claim
writes the same `worker_id='dequeue'` (line 558), and no delivery receipt is
returned to callers.

An old worker can acknowledge or reject a newer delivery after its own lease
expires and the job is reclaimed. This is a static finding from the API and
UPDATE predicates.

**Recommended change:** return a unique delivery receipt or monotonic generation
from dequeue and require it in ack/nack/lease renewal. Conditional updates should
match the receipt. Introduce the API with a compatibility plan.

**Acceptance tests:** after expiry and reclaim, the previous receipt cannot
change the new delivery; the current receipt can; duplicate acknowledgements
have a defined idempotent result.

### P1: Expired jobs can exceed max_attempts and recovery can starve

**Evidence:** expiry sweep at `src/quackapi_queue.cpp:609` sends expired running
jobs back to pending without testing attempts. Claim at line 553 increments
attempts without a cap. The max-attempts transition is only present in
`NackJob` at line 707. Repeated worker timeouts therefore lack the same retry
ceiling as explicit nacks.

Also, `HasLiveLocalLease` (line 530) suppresses expiry sweeping for the entire
queue while any local lease is live (line 607), so a continuously busy queue can
delay recovery of unrelated expired jobs.

**Recommended change:** dead-letter exhausted expired jobs; account for leases
per delivery rather than using a queue-wide sweep gate. Preserve concurrency
tests that motivated the existing mutex.

**Acceptance tests:** repeated timeouts terminate at max_attempts; an expired
job becomes available while other jobs have valid leases; concurrent claims
never duplicate an unexpired delivery.

### P1: Resource limits need a request-wide contract

**Evidence:** route TIMEOUT changes socket I/O timeouts
(`src/quackapi_server.cpp:94`, line 2608); it does not establish a DuckDB
execution deadline. GraphQL row limits are per root field and still permit many
root fields, columns, and expensive underlying operations.

**Recommended change:** separate execution deadline, I/O timeout, response byte
cap, and concurrency admission limits. Propagate cancellation into database and
outbound work; bound pending work; define shutdown drain behavior and readiness
during overload. Test expensive queries, disconnected clients, saturation, and
graceful shutdown. Do not relabel existing socket TIMEOUT as query cancellation.

### P1/P2: Rate-limit identity and isolation are weak

**Evidence:** the limiter is a process-static singleton
(`src/quackapi_server.cpp:1929`). Buckets use route name plus client identity
(line 2391), without a database/server namespace. Token mode uses the raw
Authorization header or API key (line 1938), retaining credentials in map keys
and treating accepted scheme-case/spacing variants as distinct identities.

**Recommended change:** use per-server/database state and a normalized verified
principal or keyed digest; enforce hard memory/cardinality bounds. Test identical
route names on separate database instances and equivalent credential encodings.

## Performance priorities

1. **Measure current HEAD with correct failures included.** Historical binaries
   and old scorecards do not measure the edited branch. Require identical routes,
   serialization, payloads, database paths, concurrency, and error accounting
   when comparing FastAPI. See the separate benchmark review.
2. **Reduce per-request SQL setup without leaking state.** REST intentionally
   creates a fresh connection per request at
   `src/quackapi_server.cpp:2651` to prevent TEMP/SET leakage. Any connection or
   prepared-statement reuse needs explicit reset, invalidation, and cross-request
   isolation tests. Do not reintroduce SQL-only body caching for mutable data.
3. **Batch GraphQL catalog checks.** Current execution makes a table existence
   query plus one column-existence query per requested column
   (`src/quackapi_graphql.cpp:210`, line 222) before the data query. Validate a
   selection against one bounded catalog snapshot; cache only with catalog-aware
   invalidation. Measure wide selections and many root fields.
4. **Bound outbound fanout and failure handling.** The separate outbound
   worker/thread robustness patch is implemented and regression-tested. Measure saturation, p95/p99, memory,
   errors, and cancellation rather than only successful requests/second.
5. **Budget GraphQL complexity.** Apply limits to total fields, work and response
   bytes, not only rows per selected table. Include views with expensive plans
   once view support is intentional and policy-safe.

## Feature priorities and acceptance criteria

### CREATE ROUTE syntax

Unify alternate DDL spellings into one validated route representation and produce
precise source-position errors. Prefer one canonical documented syntax for
methods, paths, parameters, auth, response format, and limits, with explicit
compatibility aliases where needed. Parse SQL structure rather than extending
ad hoc string matching.

Acceptance: equivalent spellings yield identical registry/OpenAPI behavior;
quoted strings, comments, multiline SQL, and parameter names survive round trips;
unknown/duplicate/conflicting options fail before registry mutation; CREATE OR
REPLACE does not partially update a route on validation failure; route/path
collisions across REST and GraphQL have deterministic errors.

### GraphQL

The repository already implements thin read-only GraphQL: named routes,
table allowlists, optional REQUIRE, row limits, and a custom schema endpoint.
It lacks standard introspection and is not full GraphQL. Security parity above
must come first.

Then prioritize typed schema/standard introspection, variables and validated
arguments, aliases/field merging, deterministic pagination, and consistent
GraphQL error responses. Adopt a real parser/validation model before adding
fragments, nested relationships, or mutations.

Acceptance: schema reflects exactly the permitted objects and columns; variables
are bound values; invalid documents never execute data SQL; repeated fields have
specified semantics; pagination is stable; introspection and execution share
auth/policies; complexity limits reject excessive work before execution.

Catalog correctness also needs attention: `TableExists` uses
`duckdb_tables()` at `src/quackapi_graphql.cpp:210`, while error messages and
schema comments claim view support. The schema join does not include database
identity. Add view/table and multiple-attached-database tests, and qualify the
resolved object identity consistently. This is a static finding, not a claim of
verified full view support.
