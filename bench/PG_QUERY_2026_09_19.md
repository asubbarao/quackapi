# `postgres_query()` is the comparand — redone 2026-09-19 PDT

`bench/PG_ATTACH_CONCURRENCY.md` measured DuckDB's Postgres path as
`SELECT … FROM pg.bench_rows`, a table DuckDB binds and plans itself, and
concluded from its 32-VU collapse (1,148 → 156 rps) that quackapi needs the
native libpq path. That is the wrong comparand: nobody writing a route against
Postgres has to let DuckDB plan the scan. `postgres_query()` sends the whole
statement to Postgres and streams the result back.

This note redoes the sweep with `postgres_query()` in it.

**The conclusion holds. The reason for it does not.** Native libpq is the
fastest path by a wide margin at every concurrency. But ATTACH did not collapse
at 32 VUs here, so "ATTACH falls over" is not the argument for native — the
argument is that both DuckDB-mediated paths carry per-request planner and
scanner cost that libpq does not.

## The store

A throwaway PostgreSQL 15.19 started for this measurement and thrown away
after. No service from another repository was started, used, or contacted; in
particular nothing on `:6432`.

```bash
initdb -D "$PGROOT/data" -U bench --auth=trust
pg_ctl -D "$PGROOT/data" -l "$PGROOT/pg.log" start \
  -o "-p 15432 -c listen_addresses=127.0.0.1 -c unix_socket_directories= \
      -c max_connections=400 -c fsync=off -c synchronous_commit=off"
psql -h 127.0.0.1 -p 15432 -U bench -d postgres -c 'CREATE DATABASE quackbench;'
psql -h 127.0.0.1 -p 15432 -U bench -d quackbench -c \
  "CREATE TABLE bench_rows (id INTEGER PRIMARY KEY, name TEXT NOT NULL);
   INSERT INTO bench_rows SELECT g, 'row-' || g FROM generate_series(1, 100000) AS g;
   ANALYZE bench_rows;"
```

`fsync=off` is honest here because every measured request is a primary-key
read; nothing in the sweep writes.

## The three paths

`bench/pg_routes.sql` holds all three, so a cell compares an execution path and
not a machine.

| cell | route | who plans the scan | served by |
|---|---|---|---|
| `attach` | `SELECT id, name FROM pg.bench_rows WHERE id = $id::INTEGER` | DuckDB | plain `serve_quackapi.sh` |
| `pgquery` | `postgres_query('pg', 'SELECT id, name FROM bench_rows WHERE id = ' \|\| $id::INTEGER::VARCHAR)` | Postgres | the same server |
| `native` | the `attach` route SQL, rewritten by `ToPgSql` and run over quackapi's own `PGconn` | Postgres | `serve_quackapi.sh` with `QUACKAPI_PG_DSN` |

Three things worth stating about that table:

- `postgres_query()` addresses an attached catalog by name, so `ATTACH` is the
  connection holder for both DuckDB cells. The difference measured is who plans
  the scan, not whether a catalog is attached.
- The concatenated statement is not an injection surface: `$id::INTEGER` fails
  the cast before any text is built.
- The `native` cell reuses the `attach` route on purpose. `ToPgSql` refuses
  `postgres_query` as a "duckdb-only TVF" (src/quackapi_pg.cpp), so a
  `postgres_query()` route served with `pg_dsn` silently falls back to DuckDB
  and would have measured the `pgquery` cell twice.

That the `native` cell really was native was checked from the Postgres side
rather than assumed: its DSN carries `application_name=quackapi_native`, and
under load `pg_stat_activity` showed 32 backends with that name (one per worker
thread) alongside 32 unnamed pooled backends belonging to the DuckDB server.

Both servers run `bench/serve_quackapi.sh` at its defaults (32 workers, a
derived 256-connection queue); the native one adds `QUACKAPI_PG_DSN`:

```bash
GENERATED_ROUTES_SQL=bench/pg_routes.sql QUACKAPI_DATABASE=/tmp/pgbench.duckdb \
  QUACKAPI_PORT=18093 bash bench/serve_quackapi.sh
GENERATED_ROUTES_SQL=bench/pg_routes.sql QUACKAPI_DATABASE=/tmp/pgbench_native.duckdb \
  QUACKAPI_PORT=18094 \
  QUACKAPI_PG_DSN='postgresql://bench@127.0.0.1:15432/quackbench?application_name=quackapi_native' \
  bash bench/serve_quackapi.sh
```

Load generator: `bench/loadgen.py`, 3 trials per cell, 3 measured seconds, 0.5
discarded warmup, one fixed contract `GET /…/42 -> [{"id":42,"name":"row-42"}]`.
Values are median successful RPS, median per-trial p50/p99, and the worst
successful latency across the three trials. Concurrency is never above the
server's own capacity, so no cell measures overload behaviour.

## What changed and what did not

**The 32-VU ATTACH collapse did not reproduce.** The earlier note measured
1,148 rps at 8 VUs falling to 156 at 32 — x0.14. Here ATTACH goes 5,324 -> 5,173
across the same step, x0.97: flat, not collapsing. Whatever produced that
collapse was not ATTACH against a plain Postgres.

**`postgres_query()` beats ATTACH and keeps scaling.** 2,356 -> 8,075 rps from 1
to 32 connections (x3.4) against ATTACH's 2,605 -> 5,173 (x2.0). At 32
connections it is 1.56x ATTACH throughput at two thirds the p50 and 0.69x its
p99. It is the right comparand and it is the better DuckDB path; a route that
reaches Postgres should be written this way.

At one connection ATTACH is marginally ahead (2,605 vs 2,356). That is the whole
of ATTACH's advantage: a bound table lets DuckDB plan once per statement, while
`postgres_query()` pays a describe round trip. Past a single client the pooled
concurrency of sending whole statements wins and keeps winning.

**Native libpq still wins, by more than the ratio the old numbers implied and
for a different reason.** At 32 connections native is 5.12x `postgres_query()`
and 8.00x ATTACH, at a p99 of 1.5 ms against 7.9 and 11.3. The old note's
collapsed cell implied a 48x gap over a broken ATTACH; the real gap is over a
healthy `postgres_query()`, and it is per-request DuckDB work — binder, planner,
scanner, result conversion — not a pool or a serialization point.

## What was not measured

- **The original environment.** The 1,148 → 156 collapse was measured against a
  store on `:6432` that this run is not permitted to touch. This note cannot
  reproduce or refute that measurement; it can only show that against a plain
  local PostgreSQL the same ATTACH shape does not collapse. A connection pooler
  in front of Postgres is the obvious candidate and remains untested.
- **A `postgres_query()` route on the native path.** `ToPgSql` rejects it by
  design, so there is no fourth cell.
- **Writes.** Every cell is a primary-key read. `INSERT … RETURNING`, which is
  one of the reasons the native path exists at all, is not in this sweep.
- **More than 32 connections.** The earlier note's interesting band was 1–32 and
  this note stays inside it so the two are comparable.
- **Remote latency.** Postgres is on loopback. A real network hop would shrink
  every ratio here, because it adds the same constant to all three paths.
