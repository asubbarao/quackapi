# Honest migration benchmark — observed 2026-09-18 PDT

Run ID: `20260919T044600Z-25505` (three trials, two measured seconds per
cell, 0.25-second discarded warmup). Raw artifacts remain under the ignored
`bench/results/<run-id>/` directory on the machine that ran the benchmark.

## Application and migration boundary

The pinned source is FastAPI's official multi-file “Bigger Applications” app
from `fastapi/fastapi` commit
`50113da16fec53b66b80d75e80a89296de4fa5a5`. It was selected because it is
public, dependency-light, runnable without an external store, and uses
`APIRouter`, `include_router`, shared dependencies, headers, path parameters,
and application error behavior. It is an official example rather than a
production service.

Observed `quack_from_fastapi` output:

- 8 route rows and 0 model rows.
- Local paths were `/` (3 rows), `/{item_id}` (2), `/users/`, `/users/me`, and
  `/users/{username}`.
- It emitted metadata only: method, local path, handler name, source file,
  source line, and decorator evidence.
- It did not emit router prefixes, dependency behavior, handler bodies, or
  runnable `CREATE ROUTE` SQL.

The benchmark therefore did by hand what the extractor does not yet do:
resolve `/items` and `/admin` mounts, recreate query/header dependencies,
translate seven selected handler bodies to SQL, choose response envelopes and
empty-result status bodies, and add a benchmark-only job endpoint to both
services. Every mapped route is gated against exactly one extracted row before
either server starts. This is extraction-assisted migration, not automatic
handler transpilation.

## Robustness

At 1–64 connections both services had zero contract failures, timeouts,
resets, EOFs, or other no-response attempts. Across the three 320-connection
quackapi trials there were 161,526 attempts: 117,927 successful responses,
43,597 connection resets, and 2 EOFs. These are socket failures with no HTTP
status, not 503 responses. FastAPI completed all 59,298 attempts at that level.

The 320 level is deliberately beyond quackapi's configured active plus pending
capacity (`32 + 256`). Its higher successful RPS at that level does not make the
cell a win: 26.992% of attempts received no valid response.

## Error handling

Both services passed all 9 cases: success bodies, missing query input, wrong
query token, path echo, valid item lookup, missing header, item not found,
forbidden update, and the mounted admin route. The preserved conformance JSON
contains expected and actual status/body values for every case.

## Crash durability

Each service acknowledged 64 HTTP 202 job submissions with a 3-second delayed
FastAPI task. The owning process was then sent `SIGKILL` immediately after the
client had all responses.

| stack | acknowledged | survived after process death | lost after acknowledgement |
|---|---:|---:|---:|
| FastAPI `BackgroundTasks` | 64 | 0 | 64 |
| quackapi catalog queue | 64 | 64 | 0 |

This is the durability/latency trade: FastAPI responds before its in-process
background work is durable; quackapi commits a queue row on the request path.

## What did not run

- The literal `git submodule update --init --recursive` command could not write
  the worktree's Git metadata because `.git` points under a sandbox-read-only
  path. The same pinned submodule commits were cloned directly into the two
  worktree directories, after which `GEN=ninja make release` completed.
- There is no Postgres cell. This is deliberate, not a missing result: the
  selected application needs no store. No `ATTACH (TYPE postgres)` result is
  reported or extrapolated. A future Postgres scenario must use
  `postgres_query()`.
- k6 was not used or required. The Python standard-library generator was the
  measured client and preserved every attempt.
- No production FastAPI service was benchmarked. The public pinned application
  is FastAPI's official multi-file example; results should not be generalized
  beyond its extracted and manually mapped handlers.
- Native inbound TLS, HTTP/2, multiple server processes, remote-network latency,
  and automatic translation of imperative Python business logic were not run.

## Correction: the 320-connection cell was a configuration artifact

The run above serves with `worker_threads := 32, max_pending_requests := 256` —
a capacity of 288 — and then drives **320** concurrent connections at it. The
73.0% success rate and 43,597 resets are that server refusing load past its own
configured ceiling, not a limit of quackapi. `bench/LLM_GATEWAY.md` had already
documented the mechanism and the fix: worker_threads must exceed peak inbound
concurrency, because the server holds one worker thread per in-flight request.

Re-run at the same concurrency with capacity that matches the sweep
(`QUACKAPI_WORKER_THREADS=384 QUACKAPI_MAX_PENDING_REQUESTS=1024`), three trials:

| stack | success | rps | p50 | p99 | worst max | resets | eofs |
|---|---:|---:|---:|---:|---:|---:|---:|
| fastapi | 100% | 10,216 | 30.723 ms | 39.852 ms | 49.948 ms | 0 | 0 |
| quackapi | 100% | 34,918 | 8.102 ms | 16.809 ms | 38.544 ms | 0 | 0 |

3.4x the throughput at 3.8x better p50, with nothing dropped.

Both numbers are real and both belong here. The first says what the shipped
default does under overload; the second says what the server is capable of.
`worker_threads` and `max_pending_requests` are now environment variables rather
than literals in `serve_quackapi.sh`, so a sweep can be run on either side of
capacity deliberately instead of crossing it by accident.

**The product finding underneath is the default, not the ceiling.** At 320
against a 288-capacity server, quackapi resets 43,597 connections rather than
queueing them. Degrading past capacity is expected; turning it into connection
resets with a 1.7s tail is a choice, and it is the same "fighting against
itself" shape as the worker/query thread contention — one budget silently set
too low, and no signal that it is the binding constraint.

## Follow-up 2026-09-19: overload is now a status, not a reset

The finding above was acted on. Overload past the HTTP budget answers
`503 Service Unavailable` carrying the budget that bound, and the server reports
that budget about itself through `quackapi_servers()`. Nothing about the
capacity changed: the default is still 32 workers and a 256-connection queue.

Re-measured on this machine with the same trivial route, the same load
generator, three trials of three seconds at 320 persistent connections against
`worker_threads=32` (queue 256) — the configuration whose 320-connection cell is
the 73.0% row above:

| build | attempts | 200 | 503 | resets | eofs | successful rps | p50 | p99 | worst max |
|---|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| `integration` e5bb806 | 84,094 | 62,430 | 0 | **21,623** | 41 | 6,859.5 | 2.453 ms | 1,849.363 ms | 3,033.085 ms |
| this branch | 251,095 | 197,539 | **53,556** | **0** | 0 | 21,782.5 | 1.413 ms | 361.007 ms | 1,576.238 ms |

Every attempt now ends in an HTTP status. Successful throughput tripled at the
same capacity, because a shed costs one write on the accept thread instead of a
TCP teardown and a client reconnect storm, and the p99 of the requests that did
succeed fell from 1.85 s to 0.36 s.

The same shape with a raw socket client — one worker, a one-connection queue, a
simultaneous burst, no keep-alive and no client retries:

| simultaneous connections | `integration` e5bb806 | this branch |
|---:|---|---|
| 16 | 2 × 200, **14 resets** | 2 × 200, **14 × 503**, 0 resets |
| 64 | 2 × 200, **59 resets + 3 empty replies** | 2 × 200, **62 × 503**, 0 resets |
| 120 | 2 × 200, **113 resets + 5 empty replies** | 2 × 200, **118 × 503**, 0 resets |

Three things had to change for that, and they are all one idea — the budget is
quackapi's to spend, so nothing below it may decide first:

1. **The kernel accept queue is not a policy dial.** httplib's compile-time
   `CPPHTTPLIB_LISTEN_BACKLOG` is 5, so a burst was refused by TCP with
   ECONNREFUSED before quackapi saw it. The backlog is now at least `SOMAXCONN`.
2. **A full queue answers instead of closing.** The accept loop calls a new
   `on_task_queue_full` hook; quackapi drains the request, writes the 503, and
   lets the caller close. Draining matters: a socket closed with bytes still
   queued for it sends RST, which throws the 503 away — that alone was the
   difference between 2 of 16 clients seeing the status and all 14 seeing it.
3. **The HTTP budget is one number.** `max_pending_requests` is derived from
   `worker_threads` unless it is named, so `QUACKAPI_WORKER_THREADS=384` no
   longer leaves a 256-connection queue behind, and `serve_quackapi.sh` stops
   splitting the budget by hand.

`worker_threads := 0` is now an error rather than a silent fall back to 32.
